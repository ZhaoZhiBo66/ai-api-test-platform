## 2. 退出码一定要讲清楚

| 触发情况 | 当前退出码 | 原因 |
|---|---:|---|
| 五步全部通过 | 0 | 任务 passed 且 failed=0 |
| 订单金额断言不符合预期 | 1 | 用例失败导致任务 failed |
| 平台执行被测 HTTP 请求时连接失败 | 1 | 执行器将异常记录为失败结果 |
| 任务被取消 / 平台重启导致任务 interrupted | 1 | 门禁把其他已识别终态归为未通过 |
| 门禁客户端无法连接平台、查询配置不存在或轮询超时 | 2 | main 捕获 RuntimeError |
| 其他未被统一捕获的错误，例如响应 JSON 非法 | 不保证统一为 2 | 当前脚本没有为所有协议/系统错误建立完整分类 |

这些情况中的非零退出码都会使对应 CI 步骤失败。但仓库未实现真实部署流程，也未从本地代码核实 GitHub 分支保护设置，不能据此声称已实现生产发布自动拦截。

## 6. 面试前最值得准备的追问

1. **为什么不能直接相信 AI 输出？** 能生成合法 JSON 不代表业务预期正确；所以有结构校验、规则回退、人工检查和确定性断言。
2. **为什么需要依赖图？** Token 与订单号必须先获得再使用；DFS 既补齐依赖又检测环，防止错序和死循环。
3. **异步是不是更快？** 主要让提交请求及时返回，不代表同一业务链并行；链内依赖仍然串行。
4. **如何证明发现了问题？** 开启 wrong_total，让预期 199.8 与实际 200.8 不符，查看失败断言和 CI 非零退出码。
5. **为什么独立配置被测数据库？** 平台库保存用例和结果，被测库保存业务状态，验证平台自己的数据不能证明业务接口正确。
6. **以后优先改什么？** 先完善错误分类、套件排序、自由文本脱敏、稳定持久化进度，再按真实需求引入独立任务队列和发布依赖。

详细的文件结构表、数据库关系和讲解顺序见[项目结构与面试指南](项目结构与面试指南.md)。
